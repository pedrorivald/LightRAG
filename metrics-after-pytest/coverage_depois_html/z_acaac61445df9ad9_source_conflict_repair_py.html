1#!/usr/bin/env python3 

2"""Offline source-conflict listing / repair (LR2 §5.5). 

3 

4Two or more *primary* documents can end up claiming the same canonical source 

5key (a hint-stripped basename): custom-ID inserts, legacy ids, and historical 

6basename collisions all predate the typed source resolver. A scan that meets one 

7of these classifies the file ``source_conflict`` and refuses to act — it does not 

8enqueue, delete or archive anything, because picking a winner automatically could 

9silently retire the document an operator actually wanted to keep. 

10 

11This tool is the offline half of the explicit repair flow (the online half is 

12``GET /documents/source_conflicts`` + ``POST /documents/source_conflicts/repair``). 

13It never chooses a winner: the operator names the document that keeps the source, 

14every other candidate is marked ``metadata.is_duplicate=true`` with 

15``original_doc_id=<primary>``, and **no content is ever deleted** — the demoted 

16rows keep their status and their ``full_docs`` entry, they only lose their claim 

17on the canonical source. 

18 

19"Offline" means OUT OF BAND — not through the HTTP API — and NOT "the server must 

20be stopped". Which matters, because the protection you get depends on where the 

21call runs, and only one of the two callers gets all of it: 

22 

23=========================== ============================================= 

24caller caller-side exclusion 

25=========================== ============================================= 

26``POST …/repair`` (online) real: the endpoint runs inside a server worker, 

27 or a library call from so the keyed lock, the enqueue-serialize lock 

28 inside the server and the pending-enqueue reservation all live 

29 in the shared state every worker sees 

30standalone CLI NONE of it: ``initialize_share_data(workers=1)`` 

31 builds process-LOCAL asyncio locks and a local 

32 ``_shared_dicts``, and this process never 

33 initialises ``pipeline_status``, so the locks 

34 exclude only this process and the reservation 

35 is a no-op 

36=========================== ============================================= 

37 

38Cross-process exclusion is not reachable from here: it would need the server's 

39Manager (its address and authkey are private to the server) or a persisted 

40liveness marker, which is the storage-verifiable fencing token the design 

41excludes. So: 

42 

43**Run ``--apply`` while the server is stopped or quiesced, or use the HTTP 

44endpoint instead.** A CLI commit against a live server is not silently unsafe — 

45it is guarded by the CAS and by the post-commit re-resolve, so a concurrent 

46change makes the repair FAIL LOUDLY rather than corrupt the key — but "fails 

47loudly" is the guarantee, not "cannot interleave". 

48 

49Safety model: 

50 

51- listing and ``repair`` without ``--apply`` mutate nothing; 

52- ``--apply`` re-reads the candidate set and commits only when it still matches 

53 the dry-run it just performed (compare-and-set), so a concurrent 

54 enqueue/delete fails the repair instead of being overwritten. This is the one 

55 guarantee that holds for BOTH callers, because it lives in the storage; 

56- ``verify_repair_outcome`` re-resolves the key after the commit and raises 

57 unless it is now unique on the chosen primary — the backstop that turns any 

58 interleaving the caller-side locks did not cover into a reported failure; 

59- the caller-side locks (per the table above) additionally exclude every 

60 in-deployment writer of this candidate set for the whole commit — a NEW primary 

61 being INSERTED (enqueue-serialize lock), clear/delete + scan classification + 

62 manual reset (the reservation), and the processing stage's duplicate marking 

63 (the keyed source lock, which ``_mark_duplicate_after_parse`` takes too, LR2 

64 §5.5) — for in-server callers only; 

65- a repair interrupted half-way needs no reconciliation: the finished rows 

66 already express ``duplicate`` and the rest still resolve as a conflict, so 

67 simply run it again. 

68 

69``doc_status`` and ``full_docs`` are opened — no vector store, graph store, LLM 

70or embedding model is touched. 

71 

72Usage (CLI — honors WORKING_DIR / WORKSPACE and the LIGHTRAG_* storage env vars 

73from ``.env``, same as the server):: 

74 

75 python -m lightrag.tools.source_conflict_repair list [--limit 50] [--all] 

76 python -m lightrag.tools.source_conflict_repair repair \\ 

77 --source report.docx --primary doc-abc123 [--apply] 

78 

79Usage (library — for a deployment that builds its own LightRAG):: 

80 

81 conflicts = await collect_source_conflicts(rag.doc_status, limit=50) 

82 result = await repair_one_conflict( 

83 rag.doc_status, 

84 "report.docx", 

85 "doc-abc123", 

86 workspace=rag.workspace, 

87 full_docs=rag.full_docs, # required for a commit 

88 apply=True, 

89 )

122# Pipeline states that must not overlap a source-conflict COMMIT, evaluated when 

123# the repair registers its pending-enqueue reservation. Each one owns a writer 

124# that can change the candidate set the repair just re-read, and none of them can 

125# be excluded by the enqueue-serialize lock: 

126# 

127# * ``destructive_busy`` — a clear/delete can DELETE the primary the operator 

128# chose to keep, leaving the key with no primary and the demoted rows pointing 

129# at an id that no longer exists (and the repair only demotes, so there is no 

130# supported way back); 

131# * ``scanning_exclusive`` — scan classification deletes stale FAILED stubs, one 

132# of which could be that primary; 

133# * ``manual_freeze_requested`` — the exclusive FAILED reset rewrites 

134# ``file_path`` from ``resolve_doc_file_path``, so a row whose doc_status path 

135# is a placeholder can ENTER this candidate set without ever passing the 

136# enqueue critical section. 

137# 

138# Symmetry is what makes this cheap: the scan and destructive acquires already 

139# list ``pending_enqueues`` in their own reject_when, so holding a reservation 

140# for the repair's duration buys the other direction for free — no new lock, no 

141# new lock-order edge.

163async def _repair_ingress_reservation(workspace: str): 

164 """Register the repair as in-flight ingress work for its whole duration. 

165 

166 A weighted-0 entry in ``pending_enqueue_tokens``: it charges nothing against 

167 the admission capacity but makes ``pending_enqueues`` non-zero, which is what 

168 the scan and destructive acquires already refuse on. The fences above are 

169 evaluated in the same atomic step, so the exclusion holds in both directions. 

170 

171 Registered with ``kind=SOURCE_REPAIR_RESERVATION_KIND``, and that label is 

172 load-bearing rather than descriptive: a ``manual_drain_enqueue_stalled`` 

173 fence's ``force_reset`` drops the stalled ORDINARY enqueues out of the same 

174 set, and this guard has to survive it — dropping it would re-open 

175 clear/delete, scan classification and the manual reset against a repair whose 

176 candidate re-read and demotion span may still be running. Weight cannot carry 

177 that distinction: an ordinary enqueue whose documents all dedup away 

178 re-weights itself to 0 too. 

179 

180 An uninitialised ``pipeline_status`` does NOT prove there is no server: it 

181 proves only that THIS process has none, and a standalone CLI never 

182 initialises one even when a server is running elsewhere (its shared state is 

183 a different process's). So the repair proceeds — refusing would break the 

184 stopped-server case, which is the CLI's whole purpose — but it says so, at 

185 the moment it actually applies, rather than leaving the operator to infer it 

186 from the module docstring. The CAS and the post-commit re-resolve are what 

187 keep that case honest. 

188 """ 

189 from lightrag.exceptions import PipelineNotInitializedError 

190 from lightrag.kg.shared_storage import ( 

191 SOURCE_REPAIR_RESERVATION_KIND, 

192 acquire_enqueue_reservation, 

193 get_namespace_data, 

194 get_namespace_lock, 

195 release_token_set_reservation, 

196 ) 

197 

198 try: 

199 pipeline_status = await get_namespace_data( 

200 "pipeline_status", workspace=workspace 

201 ) 

202 except PipelineNotInitializedError: 

203 logger.warning( 

204 "Source-conflict repair is committing without pipeline exclusion: " 

205 "this process has no pipeline_status, which means either no server " 

206 "is running OR one is running in ANOTHER process whose shared state " 

207 "this one cannot see. Concurrent clear/delete, scan classification " 

208 "or a manual retry are therefore NOT excluded — the compare-and-set " 

209 "and the post-commit re-resolve will fail the repair loudly if one " 

210 "interleaves. Prefer POST /documents/source_conflicts/repair while a " 

211 "server is running." 

212 ) 

213 yield 

214 return 

215 

216 pipeline_status_lock = get_namespace_lock("pipeline_status", workspace=workspace) 

217 token = f"source-repair-{uuid.uuid4().hex}" 

218 result = await acquire_enqueue_reservation( 

219 pipeline_status, 

220 pipeline_status_lock, 

221 token=token, 

222 reject_when=_REPAIR_INGRESS_FENCES, 

223 weight=0, 

224 capacity=0, 

225 kind=SOURCE_REPAIR_RESERVATION_KIND, 

226 ) 

227 if not result.acquired: 

228 raise StorageControlPlaneError(result.message) 

229 try: 

230 yield 

231 finally: 

232 await release_token_set_reservation( 

233 workspace, 

234 tokens_key="pending_enqueue_tokens", 

235 token=token, 

236 )

239@asynccontextmanager 

240async def source_conflict_repair_lock(workspace: str, canonical_source_key: str): 

241 """Hold the caller-side locks a source-conflict COMMIT requires. 

242 

243 ``repair_source_conflict`` re-reads the candidate set and demotes the losers; 

244 no backend can stop a new primary being INSERTED in between (``FOR UPDATE`` 

245 locks only the rows it saw, a snapshot transaction never sees a phantom, and 

246 Redis/OpenSearch have no transaction at all), so excluding that insert is the 

247 caller's job — see ``DocStatusStorage.repair_source_conflict``. 

248 

249 Three things, in this TOTAL order — outermost first: 

250 

251 1. the workspace's enqueue-serialize lock — the one that excludes the 

252 phantom, because it is the same lock the enqueue critical section 

253 (``filter_keys`` → dedup → ``doc_status.upsert``) holds; 

254 2. a keyed lock on the canonical source key (:func:`source_candidate_set_lock`) 

255 — serializes concurrent repairs of the SAME key without blocking other 

256 keys, and, since LR2 §5.5 requires exclusion against every writer that can 

257 change this key's candidate set, it is the SAME lock the processing stage's 

258 duplicate marking now takes (``_mark_duplicate_after_parse``); 

259 3. a pending-enqueue reservation (see :func:`_repair_ingress_reservation`), 

260 which excludes the writers the enqueue-serialize lock cannot: clear/delete, 

261 scan classification, and the manual exclusive reset. 

262 

263 This order used to be keyed → enqueue_serialize, with a note that anyone 

264 extending the keyed ``DocSource`` lock to another writer MUST flip it first, 

265 because it was INVERTED relative to the enqueue path (which holds 

266 enqueue_serialize and would naturally reach for a keyed source lock inside 

267 it). Extending it to the duplicate-marking path is exactly that change, so 

268 the flip happened with it: ``enqueue_serialize → DocSource → pipeline_status`` 

269 is now the total order every holder of more than one agrees on, and it is the 

270 order the enqueue path could adopt without a cycle. The marking path takes 

271 only (2) and, inside it, ``pipeline_status`` for its owner check — same 

272 direction, no cycle. 

273 

274 Every one of these is PROCESS-LOCAL machinery, so the scope is one 

275 deployment — its worker processes included, because they share the Manager 

276 the master created — and nothing beyond it. Two consequences, the second of 

277 which is easy to miss: 

278 

279 * a repair run against a database another deployment is writing to keeps the 

280 phantom window; 

281 * **the standalone CLI is such an "other deployment"**. It calls 

282 ``initialize_share_data(workers=1)``, so these locks are asyncio objects in 

283 its own process and the reservation finds no ``pipeline_status`` at all. 

284 Everything here holds for the HTTP endpoint and for a library call inside a 

285 server worker; for the CLI it is inert, and the CAS plus 

286 :func:`verify_repair_outcome` are the whole guarantee (see the module 

287 docstring). 

288 """ 

289 # Imported lazily: the CLI initializes shared storage in main(), and 

290 # importing at module scope would bind before that happens. 

291 from lightrag.kg.shared_storage import get_namespace_lock 

292 

293 async with get_namespace_lock( 

294 ENQUEUE_SERIALIZE_LOCK_NAMESPACE, workspace=workspace 

295 ): 

296 async with source_candidate_set_lock(workspace, canonical_source_key): 

297 async with _repair_ingress_reservation(workspace): 

298 yield

326async def repair_one_conflict( 

327 doc_status: Any, 

328 canonical_source_key: str, 

329 primary_doc_id: str, 

330 *, 

331 workspace: str = "", 

332 full_docs: Any = None, 

333 apply: bool = False, 

334) -> Any: 

335 """Dry-run one repair and, with ``apply``, commit it with that fresh token. 

336 

337 The commit echoes the count/fingerprint the dry-run just returned, so the 

338 backend still fails closed if the candidate set changes in between — the CAS 

339 is not bypassed by automating the two steps, only the copy-paste is. 

340 

341 The commit additionally runs under the caller-side locks the storage contract 

342 requires: a keyed lock on the canonical source key (serializing concurrent 

343 repairs of the same key) plus the workspace's enqueue-serialize lock, which 

344 is what actually excludes a new primary being INSERTED between the backend's 

345 re-read and its demotions — no backend can block that phantom on its own. A 

346 phantom that lands BEFORE the commit is already caught by the CAS (a new 

347 primary changes both the count and the fingerprint); the locks close the one 

348 window the CAS cannot see, inside the backend call itself. 

349 ``workspace`` must be the LightRAG instance's workspace (``rag.workspace``), 

350 NOT ``doc_status.workspace``: a backend may override its own workspace from 

351 the environment, and a lock keyed on the wrong one excludes nothing. 

352 

353 ``full_docs`` is REQUIRED for a commit (``apply=True``): it is what the 

354 contentless-primary refusal reads, and an unverified primary is refused with 

355 :class:`StorageControlPlaneError` rather than granted the source — see 

356 :func:`refuse_a_contentless_primary` for why the asymmetry is not close. It 

357 cannot live in the backend: a doc_status storage has no handle on full_docs. 

358 Dry-runs (and ``collect_source_conflicts``) mutate nothing and need none. 

359 """ 

360 if not apply: 

361 return await doc_status.repair_source_conflict( 

362 canonical_source_key, 

363 primary_doc_id=primary_doc_id, 

364 # Ignored in dry-run mode by contract. 

365 expected_candidate_count=0, 

366 expected_candidate_fingerprint="", 

367 dry_run=True, 

368 ) 

369 # The dry-run stays INSIDE the lock, but its token is never refreshed: the 

370 # CAS must still be able to refuse. A candidate set that moved before the 

371 # lock was taken SHOULD 409 rather than be silently accepted. 

372 async with source_conflict_repair_lock(workspace, canonical_source_key): 

373 # Inside the lock: the row could have lost its content — or gained a 

374 # content-hash twin — between the operator reading the listing and this 

375 # commit. 

376 await refuse_an_unusable_primary( 

377 doc_status, full_docs, canonical_source_key, primary_doc_id 

378 ) 

379 dry = await doc_status.repair_source_conflict( 

380 canonical_source_key, 

381 primary_doc_id=primary_doc_id, 

382 expected_candidate_count=0, 

383 expected_candidate_fingerprint="", 

384 dry_run=True, 

385 ) 

386 result = await doc_status.repair_source_conflict( 

387 canonical_source_key, 

388 primary_doc_id=primary_doc_id, 

389 expected_candidate_count=dry.candidate_count, 

390 expected_candidate_fingerprint=dry.fingerprint, 

391 dry_run=False, 

392 ) 

393 # Verify the OUTCOME, still inside the locks, instead of inferring it 

394 # from "the demotions were committed". ``committed=True`` only claims 

395 # that the demotions named in the result landed; the key being unique is a 

396 # separate claim, so it is checked rather than assumed. 

397 # 

398 # Every in-deployment writer of this candidate set is now excluded for the 

399 # whole span: enqueue by the enqueue-serialize lock, clear/delete + scan 

400 # classification + manual reset by the reservation, and the processing 

401 # stage's duplicate marking by the keyed source lock it now takes too 

402 # (LR2 §5.5). So this verification is a backstop, not the primary guard — 

403 # which is what it must be, because two things remain outside every lock 

404 # here: the standalone CLI (its locks are process-local and it has no 

405 # pipeline_status at all) and any second deployment writing the same 

406 # database. 

407 await verify_repair_outcome( 

408 doc_status, canonical_source_key, primary_doc_id, result 

409 ) 

410 return result

413async def refuse_a_contentless_primary(full_docs: Any, primary_doc_id: str) -> None: 

414 """Refuse to hand a canonical source to a row with no ``full_docs`` content. 

415 

416 Such a row is an unprocessable stub, and keeping it is self-defeating twice 

417 over. It can never be processed, so the source key ends up owned by a 

418 document that will never exist; and it is exactly what scan classification 

419 deletes on sight (``_ScanFileClass.STALE_STUB`` fires only when 

420 ``_confirm_full_docs_absent`` is True), so the next scan would delete the 

421 primary and leave the demoted rows pointing at a missing id — with no way 

422 back, since a repair only demotes and refuses a ``primary_doc_id`` that is 

423 not a current candidate. 

424 

425 Checking here is what removes that interaction at the root, and it is 

426 strictly better than locking the scan's delete path against the repair: it 

427 costs one strict read on an operator-invoked path instead of a lock on scan 

428 classification, and it also catches the plain operator mistake of choosing a 

429 stub when no scan is running at all. 

430 

431 A CONFIRMED absence refuses with 

432 :class:`SourceConflictPrimaryUnusableError` (409 — pick another primary). 

433 EVERY other answer than "it has content" refuses with 

434 :class:`StorageControlPlaneError` (503 — retry once storage is back): a read 

435 that failed, a backend with no strict point reads, and no ``full_docs`` handle 

436 at all. Unverified is not the same as verified, and the asymmetry is not 

437 close: the demotions are irreversible (a repair only demotes, and a key with 

438 no candidate left cannot be repaired again), while a 503 costs the operator a 

439 retry of an operation that has no deadline — the conflict has been sitting 

440 there since before they looked at it. 

441 

442 The no-strict-reads branch used to warn and proceed, reasoning that scan 

443 classification cannot delete the stub on such a backend either 

444 (``_confirm_full_docs_absent`` returns ``None`` for the same reason, so the 

445 STALE_STUB exit never fires). That covers only ONE of the two harms: a stub 

446 can never be processed, so handing it the canonical source leaves the key 

447 owned by a document that will never exist, whatever the scan does. Every 

448 in-tree KV backend declares ``supports_strict_point_reads = True``, so this 

449 only refuses a third-party backend that cannot answer the question. 

450 """ 

451 if full_docs is None: 

452 raise StorageControlPlaneError( 

453 f"Cannot confirm whether {primary_doc_id} has full_docs content: no " 

454 f"full_docs handle was provided. A source-conflict COMMIT requires " 

455 f"one — its demotions are irreversible, so an unverified primary is " 

456 f"refused rather than granted the source." 

457 ) 

458 if not getattr(full_docs, "supports_strict_point_reads", False): 

459 raise StorageControlPlaneError( 

460 f"{type(full_docs).__name__} has no strict point reads, so it cannot " 

461 f"confirm whether {primary_doc_id} has content; refusing to commit " 

462 f"irreversible demotions on an unverified primary. A contentless stub " 

463 f"can never be processed, so it would own the source forever." 

464 ) 

465 try: 

466 content = await full_docs.get_by_id_strict(primary_doc_id) 

467 except Exception as read_error: 

468 raise StorageControlPlaneError( 

469 f"Could not confirm whether {primary_doc_id} has full_docs content " 

470 f"({read_error}); refusing to commit irreversible demotions on an " 

471 f"unverified primary. Retry once full_docs is reachable." 

472 ) from read_error 

473 if content: 

474 return 

475 raise SourceConflictPrimaryUnusableError( 

476 f"Document {primary_doc_id} has no full_docs content: it is an " 

477 f"unprocessable stub, so it cannot own a canonical source. Pick a " 

478 f"primary that has content — a scan would delete this row and leave the " 

479 f"demoted documents pointing at an id that no longer exists.", 

480 reason=SourceConflictPrimaryUnusableError.REASON_NO_CONTENT, 

481 )

484async def refuse_a_primary_whose_content_lives_elsewhere( 

485 doc_status: Any, canonical_source_key: str, primary_doc_id: str 

486) -> None: 

487 """Refuse a primary the PROCESSING stage is already destined to demote. 

488 

489 The commit DOES exclude the processing stage for its whole span — the keyed 

490 source lock it holds is the same one ``_mark_duplicate_after_parse`` takes 

491 (LR2 §5.5) — but exclusion only ORDERS the two operations; it cannot keep a 

492 primary usable after it releases. A marking that was already destined to 

493 demote this row simply lands the moment the lock is free, and the key the 

494 operator was just told is settled has no primary again. So the lock and this 

495 refusal answer different questions, and this one belongs where the 

496 contentless-stub refusal already sits: BEFORE the irreversible demotions, by 

497 refusing a primary that cannot keep the source. 

498 

499 A primary whose content hash is already held by a document under a DIFFERENT 

500 canonical source is exactly that: when it is parsed, the post-parse duplicate 

501 check will mark it FAILED-duplicate of that holder and delete its 

502 ``full_docs`` body, and the key it was just given ends with no primary — the 

503 state the repair endpoint cannot settle, since it only accepts a current 

504 primary candidate. 

505 

506 Bounded on purpose, and partial by construction: 

507 

508 * a primary with no ``content_hash`` yet (an unparsed PENDING candidate — an 

509 ordinary conflict candidate) cannot be checked at all: nobody knows what 

510 its content will be. If it later turns out to duplicate another document, 

511 the outcome is the ordinary content-dedup steady state (the content lives 

512 under the other document, and this key has no primary because the file's 

513 content is not its own), and no content is lost. That residual is 

514 irreducible without parsing the document inside the repair; 

515 * a match that claims THIS canonical source is not a reason to refuse — it is 

516 one of the candidates this repair is about to demote (or one an earlier 

517 repair already demoted). The lookup returns only the earliest holder, so a 

518 same-key holder that sorts first also hides any further one: the check 

519 abstains rather than guess, which is the same partiality with the same 

520 residual as the case above. 

521 

522 The lookup is fail-closed by contract (``get_doc_by_content_hash`` raises 

523 rather than reporting a transport failure as "no holder"), and the strict 

524 hydration of the primary's own row propagates too, so an unreadable state 

525 refuses the commit instead of skipping the check. 

526 """ 

527 rows = await doc_status.get_full_docs_by_ids([primary_doc_id], strict=True) 

528 primary_row = rows.get(primary_doc_id) 

529 if primary_row is None:

531 # the message that sends the operator to re-list the conflict.
