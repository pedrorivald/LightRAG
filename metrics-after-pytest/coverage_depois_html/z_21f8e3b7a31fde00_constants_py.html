103# DEFAULT_R_SEPARATORS: cascade tried by langchain RecursiveCharacterTextSplitter. 

104# Order matters — strongest boundary first: paragraph (\n\n) > line (\n) > 

105# Chinese sentence-end (。！？) > Chinese semi-clause (；，) > space > char. 

106# English sentence-ending punctuation (.?!) is intentionally NOT included 

107# because RecursiveCharacterTextSplitter does literal-string splitting, so 

108# "." would also split numerals (``0.95``) and abbreviations (``e.g.``). 

109# The English path falls through space / char as before. 

110DEFAULT_R_SEPARATORS: tuple[str, ...] = ( 

111 "\n\n", 

112 "\n", 

113 "。", 

114 "！", 

115 "？", 

116 "；", 

117 "，", 

118 " ", 

119 "", 

120) 

121# Bounds on any separator cascade, wherever it comes from. The recursive splitter 

122# descends one level per remaining separator and re-scans the text at every level, 

123# so total work is O(len(separators) x len(text)); with both factors supplied by 

124# one request that is an amplifier (GHSA-26pm-px5v-8c4w). The request model caps 

125# the list, but CHUNK_R_SEPARATORS, addon_params, direct SDK calls and per-doc 

126# snapshots persisted before that cap existed all bypass it, so the chunker 

127# normalizes whatever it is handed. 64 leaves ample room for a multi-language 

128# cascade — the built-in one is 9 entries. 

129MAX_R_SEPARATORS = 64 

130# Per-entry length. A single huge separator is re-escaped and re-scanned at every 

131# level, so it is expensive for the same reason a long list is. 

132MAX_R_SEPARATOR_CHARS = 256

159# Decompression budget for the native DOCX engine. A .docx is a ZIP, so the 

160# bytes it costs to parse are its UNCOMPRESSED size, which no other control on 

161# the ingestion path bounds: MAX_UPLOAD_SIZE bounds the compressed artifact on 

162# disk and MAX_REQUEST_BODY_BYTES bounds the request body. A 449 KiB .docx 

163# declaring 200 MiB of document.xml passed both and drove peak RSS past 1.1 GB 

164# (GHSA-2wpj-ffvv-2pq8). 

165# 

166# Both quantities come from the ZIP central directory, so the check costs one 

167# infolist() and no decompression. A central directory that UNDERSTATES a 

168# member is self-limiting rather than a bypass: CPython's zipfile stops 

169# decompressing at the declared file_size and then fails the CRC, so a liar 

170# buys at most the size it declared — which is the size this budget bounds. 

171# 

172# The ratio gate is what actually closes the amplification: 512 MiB alone would 

173# still let a ~1 MB upload expand 500x. It is enforced both archive-wide and 

174# against the cumulative expansion by which individual members exceed their 

175# ratio budgets, so member splitting cannot dilute it. The allowance is the 

176# fixed DEFAULT_DOCX_RATIO_FLOOR_BYTES plus archive bytes outside those members 

177# at 1:1: real stored media can support repetitive XML, while padding cannot buy 

178# another ratio-cap multiple of expansion. 

179# The same budget governs the other OPC/OOXML formats the legacy engine parses 

180# locally — .pptx (python-pptx) and .xlsx (openpyxl) are the identical ZIP-bomb 

181# class — so the DOCX_* knobs below bound all three, enforced in the legacy 

182# ``extract_text`` dispatcher as well as the native docx engine. 

183# Env: DOCX_MAX_UNCOMPRESSED_BYTES / DOCX_MAX_COMPRESSION_RATIO / 

184# DOCX_RATIO_FLOOR_BYTES / DOCX_MAX_ENTRIES, read live at parse time. 

185DEFAULT_DOCX_MAX_UNCOMPRESSED_BYTES = 512 * 1024 * 1024 

186DEFAULT_DOCX_MAX_COMPRESSION_RATIO = 100 

187# RATIO_FLOOR_BYTES exempts small content from the two ratio views above; it is 

188# not a gate itself. Archive-wide it acts as a size THRESHOLD: the ratio is only 

189# checked once the uncompressed total exceeds it. Per member it acts as a fixed 

190# ALLOWANCE, added to the 1:1 supporting-archive-bytes budget for the cumulative 

191# excess by which over-ratio members overrun their individual ratio budgets — so 

192# it is an amount of tolerated expansion there, not a file-size cut-off. A 

193# non-positive value removes the exemption (strictest) in both views, it does not 

194# disable the ratio gate. See lightrag/parser/docx/zip_budget.py. 

195DEFAULT_DOCX_RATIO_FLOOR_BYTES = 16 * 1024 * 1024
