37@dataclass 

38class NetworkXStorage(BaseGraphStorage): 

39 """File-backed knowledge-graph storage built on ``networkx.Graph``. 

40 

41 The whole graph lives in process memory and is published by rewriting one 

42 GraphML file at ``working_dir/[workspace/]graph_<namespace>.graphml``. That 

43 file is the ONLY cross-process synchronization surface. 

44 

45 **Full contract: ``docs/design/NetworkXSingleWriterContract.md`` — read it 

46 before changing anything in this class.** Comments below cite its sections 

47 by name ("the contract doc"). It carries the two-channel commit 

48 fence, the recovery-reload rule, the dirty-graph backstop, the accepted 

49 residues, and the alternatives already rejected (notably reload-then-replay). 

50 

51 The rules this class is correct only while they hold: 

52 

53 * **Single writer per workspace.** At most one process runs ``upsert_*`` / 

54 ``delete_*`` / ``remove_*`` / ``index_done_callback`` at a time. The 

55 pipeline supplies this through its ``busy`` reservation; the admin flows 

56 through ``LightRAG._admin_write_gate``, which this class requests by 

57 declaring ``requires_single_writer = True`` (the only storage that does). 

58 * **networkx calls are synchronous**, so they cannot be preempted on the 

59 event loop — which is why the mutators do not hold ``_storage_lock``. The 

60 one exception is the GraphML serialization, which runs in a worker thread; 

61 ``_commit_gate`` re-establishes the exclusion for it. 

62 * **Eventual consistency is sufficient** for readers: a read between a 

63 writer's mutation and its commit may return the previous snapshot. 

64 

65 Two things a new caller of the mutators must do, both load-bearing: make its 

66 chunk-tracking row durable BEFORE the mutation call (not merely before the 

67 flush — an uncommitted ``upsert_node`` already sits in the process-wide 

68 graph, where the next flush publishes it), and run inside the admin-write 

69 gate or the pipeline reservation. Bypassing either trips the dirty-graph 

70 backstop, which fails the commit loudly rather than losing the write 

71 silently. 

72 

73 A commit publishes the WHOLE namespace, so any writer's flush also publishes 

74 every other writer's pending mutation here, half-finished ones included. 

75 

76 Supported for small-scale testing and validation only; production 

77 deployments run a server-backed graph store. 

78 """

191 def _gate(self) -> asyncio.Event: 

192 """The commit gate: set except while this process is serializing. 

193 

194 See *Commit gate* in the contract doc. Lazily created so the 

195 ``asyncio.Event`` binds to whichever loop first waits on it, which is 

196 never the loop-less ``__post_init__``. 

197 

198 Rebuilt when the running loop changes. An ``asyncio.Event`` binds to a 

199 loop the first time a ``wait()`` actually suspends on it, and from then 

200 on ``wait()`` from any other loop raises "is bound to a different event 

201 loop". A single instance CAN legitimately outlive its loop: the 

202 synchronous wrappers let calls through on a fresh loop once the original 

203 ``owning_loop`` has closed (see ``_run_sync`` — the common 

204 ``rag = asyncio.run(initialize_rag())`` shape), and a gate bound during 

205 some earlier commit would then break the next one. 

206 

207 Rebinding is safe rather than a race: a commit in flight holds 

208 ``_storage_lock`` and runs on the loop being replaced, so reaching here 

209 on a different loop means no commit of ours is outstanding and an open 

210 gate is the correct state. Lazily rebuilt here, not eagerly in 

211 ``initialize()``, because that is not where the loop change shows up. 

212 """ 

213 loop = asyncio.get_running_loop() 

214 if self._commit_gate is None or self._commit_gate_loop is not loop: 

215 self._commit_gate = asyncio.Event() 

216 self._commit_gate.set() 

217 self._commit_gate_loop = loop 

218 return self._commit_gate

278 def _count_unannounced_peer_commit_locked( 

279 self, sampled: file_fingerprint.Fingerprint | object 

280 ) -> bool: 

281 """Count a peer commit no notification announced. True if it counted. 

282 

283 Precondition: the caller holds ``_storage_lock``, and has NOT reloaded 

284 yet -- a reload adopts the file, after which the question cannot be 

285 asked any more. The caller logs; this decides and counts, so 

286 ``_missed_notification_reloads`` has exactly one increment site. 

287 

288 ``_missed_notification_reloads`` is the evidence the writer-side 

289 ``os.utime`` decision waits on (see ``kg.file_fingerprint``), so it has 

290 to count *unannounced on-disk states*, not detections of them -- one 

291 per distinct state this process found, however many detections or 

292 reload attempts that took. (Per state, not per commit: this is a state 

293 channel, so peer commits that batch into one observation are one 

294 increment. ``kg.file_fingerprint`` records that as one of the two 

295 by-design blind spots.) State and detection are not the same thing, 

296 in both directions: 

297 

298 * **Undercount.** The recovery flag wins over both channel tests and 

299 one reload discharges all of them, so a peer commit that arrives 

300 while recovery is pending would be handled and never counted. That 

301 is why the recovery branches -- and the failed-save handler's own 

302 recovery reload -- call this at all. 

303 * **Overcount.** A reload that raises leaves ``_loaded_fingerprint`` 

304 and ``_recovery_reload_pending`` exactly as they were, so the same 

305 peer commit is re-detected by every later call -- and, counted at 

306 detection, re-counted every time, without bound. Persistent 

307 unreadability is not exotic here: a failed reload is what arms 

308 recovery in the first place. ``_counted_peer_fingerprint`` plus 

309 ``file_fingerprint.counts_as_a_new_lost_notification`` (shared with 

310 the vector backends, which have the same counter and had the same 

311 defect) makes the count once-per-state instead of once-per-attempt. 

312 See that function for what it does and does not distinguish. 

313 

314 ``sampled`` is the caller's own sample, and the caller MUST hand the 

315 same one to ``_reload_locked``. Sampling independently here would make 

316 the count and the adoption describe two different observations, and a 

317 transient ``UNREADABLE`` on this one alone would then be uncountable 

318 forever: this helper would skip the increment while the reload's own 

319 successful stat adopted the peer state, erasing the divergence that 

320 would have let a later call count it. Sharing one sample keeps the two 

321 outcomes tied -- either the event is counted, or no fingerprint is 

322 adopted that could suppress counting it next time. The vector backends 

323 share their pre-read sample for exactly this reason. 

324 

325 Self-contained otherwise: it re-tests the flag and re-applies the full 

326 divergence decision even where the caller's branch condition already 

327 established them, so no site can count by satisfying only half the 

328 condition. It re-*observes* nothing, though -- the divergence test runs 

329 against ``sampled`` too. The flag re-read is safe to repeat because it 

330 is not an observation of the file: a flag that turned True in between 

331 means the notification arrived after all, and declining to count that 

332 is correct. 

333 """ 

334 if self.storage_updated.value: 

335 return False 

336 if not self._peer_commit_detected(sampled): 

337 return False 

338 if not file_fingerprint.counts_as_a_new_lost_notification( 

339 sampled, self._counted_peer_fingerprint 

340 ): 

341 logger.debug( 

342 f"[{self.workspace}] The peer commit to {self._graphml_xml_file} " 

343 "is the one already counted, or its stat failed; this is a " 

344 "retry of a reload that did not land, not a second lost " 

345 "notification." 

346 ) 

347 return False 

348 self._counted_peer_fingerprint = file_fingerprint.adopted(sampled) 

349 self._missed_notification_reloads += 1 

350 return True

352 def _reload_locked( 

353 self, 

354 fingerprint: file_fingerprint.Fingerprint | object | None = None, 

355 *, 

356 arm_dirty_discard: bool = True, 

357 ) -> None: 

358 """Reload ``self._graph`` from disk and satisfy BOTH fence channels. 

359 

360 Precondition: the caller holds ``_storage_lock``. 

361 

362 One reload, one post-condition, whichever condition fired: record the 

363 new fingerprint, clear the flag, **and** clear the pending recovery 

364 reload. Open-coding any of the three is how this fence rots -- a missed 

365 recovery clear is sticky and makes every later commit decline forever. 

366 On FAILURE the pending recovery reload is armed before the exception 

367 leaves, so the invariant is total: after a return the graph matches the 

368 file, after a raise a reload is owed and recorded. 

369 

370 ``arm_dirty_discard`` is the dirty-graph backstop switch: ``True`` (the 

371 default) records a discarded dirty graph for the next commit to refuse, 

372 ``False`` only logs it. The three exempt callers pass ``False``. 

373 

374 ``fingerprint`` lets a caller that already sampled pass its own sample 

375 in, so the count and the adoption describe one observation; omitted, 

376 this samples for itself. ``None`` is unambiguous as "not given" -- 

377 ``_stat_fingerprint`` returns a tuple or ``UNREADABLE``, never ``None``. 

378 

379 **Raises** ``OSError`` without loading anything when the sample is 

380 ``UNREADABLE``: a reload has to record what it read, and an unsampled 

381 file cannot be recorded. Every caller's ``except`` already treats a 

382 failed reload as "the divergence stands, retry next call". 

383 

384 Synchronous on purpose: it adds no suspension point inside 

385 ``_get_graph``'s lock body, which the commit-gate reasoning depends on. 

386 

387 Why each exemption, what an ``UNREADABLE`` sample costs either way, and 

388 why callers arm recovery at the branch entry rather than relying on the 

389 backstop here: ``docs/design/NetworkXSingleWriterContract.md``. 

390 """ 

391 try: 

392 self._reload_or_arm_locked(fingerprint, arm_dirty_discard=arm_dirty_discard) 

393 except BaseException: 

394 # ARM, then re-raise. This is the whole reason the reload is not 

395 # open-coded at its five call sites: a reload that fails leaves 

396 # this process holding a graph that does not match the file, and 

397 # the operation that asked for it fails -- so the mutations in it 

398 # belong to a batch that has just been reported as failed. Exactly 

399 # the state _recovery_reload_pending exists for, and until this 

400 # was the single choke point only the failed-SAVE path armed it. 

401 # 

402 # What the four other sites left open: the flag and the 

403 # fingerprint stay as they were, which keeps the divergence 

404 # visible only while the file can be sampled. Let the stat keep 

405 # failing and both channels report "no change" (the documented 

406 # degrade to the flag alone), so the next commit passes the fence 

407 # and serializes that graph -- overwriting the peer's durable 

408 # commit AND publishing work already reported as FAILED. Armed, 

409 # the same commit declines instead and the next successful reload 

410 # discards it. 

411 # 

412 # BaseException, not Exception: a CancelledError delivered inside 

413 # the load leaves the same divergence, and losing the record of it 

414 # because the caller went away is how it becomes permanent. 

415 self._recovery_reload_pending = True 

416 raise

427 every post-condition and every refusal documented on 

428 ``_reload_locked`` lives here. 

429 """

431 # *Cross-process sync protocol*.

436 # unsafe twice over, and both ways cost data: 

437 # 

438 # * ``load_nx_graph`` gates on ``os.path.exists``, which reports 

439 # False for *any* stat failure -- the same failure that produced 

440 # UNREADABLE. So the load returns None, ``or nx.Graph()`` makes 

441 # that an EMPTY graph, and while the stat keeps failing the fence 

442 # cannot object (``divergence_detected`` returns False for

444 # the real file. That is the outcome *Cross-process sync 

445 # protocol* names as the one thing this fence must never do. 

446 # * Even with the file readable and only its stat failing, 

447 # ``adopted(UNREADABLE)`` records ``None``, against which every 

448 # state is a divergence -- so the NEXT ``_get_graph`` reloads 

449 # again, and that second reload discards whatever this process 

450 # mutated in between. The commit after it then succeeds without

452 # silent partial loss. See ``file_fingerprint.adopted``. 

453 # 

454 # Raising instead costs work, never data: the flag and the 

455 # fingerprint are left exactly as they were, so the divergence 

456 # stays visible and the next call retries the reload; the

513 async def _get_graph(self): 

514 """Return the live ``networkx.Graph``, reloading from disk if needed. 

515 

516 This is the **single entry point** every public method funnels 

517 through to obtain ``self._graph``. It is also the **only place 

518 readers transition to a fresher on-disk snapshot**: when another 

519 process has committed (via ``index_done_callback``), the next call 

520 here rebuilds ``self._graph`` by re-parsing the entire GraphML file. 

521 networkx has no incremental sync API — the reload is 

522 unconditionally a full file reload. 

523 

524 Two tests decide that, and both must stay — see *Cross-process sync 

525 protocol* in the contract doc for why neither is redundant: this 

526 process's ``storage_updated`` flag, and the GraphML file's 

527 ``(st_mtime_ns, st_size)`` against the fingerprint recorded when this 

528 process last loaded or wrote it. 

529 

530 Two conditions that are not channels are tested alongside them: the 

531 process-local recovery reload FIRST (see *Recovery reload*), and an 

532 unresolved fingerprint — a recorded ``None`` — LAST. The file channel 

533 settles that one itself whenever it can sample: any concrete state is 

534 a divergence against ``None``, so it reloads. What the last test 

535 covers is the case where it cannot, since an unreadable ``stat`` 

536 reports "no change" and would leave the question open across a 

537 mutation. Each branch below says why. 

538

540 branch fires in the writer process: the writer resets its own flag
