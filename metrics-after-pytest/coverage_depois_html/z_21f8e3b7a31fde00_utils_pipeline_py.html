70def apply_trusted_sentence_split_regex( 

71 v_opts: dict[str, Any], 

72 addon_params: Any, 

73 *, 

74 doc_id: str | None = None, 

75) -> dict[str, Any]: 

76 """Force ``sentence_split_regex`` to the live, operator-controlled value. 

77 

78 ``v_opts`` comes from the per-doc ``chunk_options`` snapshot persisted in 

79 ``full_docs``. Every other chunker parameter deliberately wins from that 

80 snapshot so a document re-processes reproducibly across env changes; this 

81 one key is the exception, and is re-read live from 

82 ``addon_params['chunker']['semantic_vector']`` (seeded by 

83 ``CHUNK_V_SENTENCE_SPLIT_REGEX``) on every run. 

84 

85 The reason is that the value is splatted into ``re.split`` against the 

86 document body. A backtracking pattern such as ``(a+)+$`` runs for 

87 exponential time, and CPython's regex engine holds the GIL throughout, so 

88 the semantic-vector chunker's ``asyncio.to_thread`` hop does not keep the 

89 event loop alive — the worker process stops serving every endpoint until 

90 it is restarted (GHSA-32jh-39m7-8x84, CWE-1333). 

91 

92 ``chunk_options`` is snapshotted at ENQUEUE time, before chunking runs, so 

93 a build that still accepted the field on ``/documents/text`` persisted the 

94 attacker's pattern to storage *and* left the document in ``PROCESSING`` 

95 when the worker froze. ``PROCESSING`` is an auto-resume status, so without 

96 this scrub an upgraded server would reload the stored pattern and freeze 

97 again on every restart — a boot loop that restarting cannot clear. 

98 Rejecting the field at the request model only protects new requests; this 

99 is what disarms snapshots already on disk. 

100 

101 The replacement is unconditional, so provenance never has to be 

102 reconstructed — which also means a *legitimate* per-document pattern 

103 handed to ``apipeline_enqueue_documents(chunk_options=…)`` by an SDK caller 

104 is discarded the same way. That is intended: the only supported way to 

105 change the splitter is ``addon_params['chunker']['semantic_vector']`` / 

106 ``CHUNK_V_SENTENCE_SPLIT_REGEX``. Because the loss is silent from the 

107 caller's side, every discard of a *differing* snapshot value is logged at 

108 WARNING with the doc id. 

109 

110 This is the single point where the guarantee is enforced: the ``"V"`` 

111 dispatch in :meth:`_PipelineMixin.process_single_document` is currently the 

112 only consumer of ``chunk_options['semantic_vector']``. Any new consumer 

113 MUST route through this helper — the poisoned value is left in place in 

114 ``full_docs`` (inert, not rewritten), so an unscrubbed read would revive it. 

115 

116 Returns a new dict; ``v_opts`` is not mutated. 

117 """ 

118 sanitized = {k: v for k, v in v_opts.items() if k != "sentence_split_regex"} 

119 chunker_cfg = (addon_params or {}).get("chunker") or default_chunker_config() 

120 live_regex = (chunker_cfg.get("semantic_vector") or {}).get("sentence_split_regex") 

121 if live_regex: 

122 sanitized["sentence_split_regex"] = live_regex 

123 

124 snapshot_regex = v_opts.get("sentence_split_regex") 

125 if snapshot_regex is not None and snapshot_regex != live_regex: 

126 # Audit line for a decision with consequences: either a pre-fix build 

127 # persisted an attacker pattern (the case this helper exists for), or 

128 # an SDK caller's per-doc value is being dropped. The pattern is 

129 # untrusted text, so log a bounded repr rather than the raw string. 

130 shown = repr(snapshot_regex) 

131 if len(shown) > 120: 

132 shown = shown[:117] + "..." 

133 logger.warning( 

134 "Discarded persisted sentence_split_regex %s for doc %s; using the " 

135 "operator-configured pattern instead (GHSA-32jh-39m7-8x84). Set " 

136 "CHUNK_V_SENTENCE_SPLIT_REGEX or addon_params['chunker']" 

137 "['semantic_vector'] to change the V sentence splitter.", 

138 shown, 

139 doc_id or "<unknown>", 

140 ) 

141 return sanitized

294# Long-lived per-document metadata fields that must survive every 

295# doc_status state transition. ``process_options`` records the user's 

296# per-file processing strategy at enqueue time and is read by analyze / 

297# chunk / KG-skip stages and by admin/list APIs throughout the document's 

298# lifetime, so we cannot let an intermediate transition (PARSING / 

299# ANALYZING / PROCESSING / PROCESSED / FAILED upsert) clobber it. 

300# ``parse_warnings`` records non-fatal parser warnings (e.g. legacy docx 

301# tables missing ``w14:paraId``) that admins should be able to surface 

302# alongside the document record after PROCESSED. 

303# ``chunk_opts`` is written when entering PROCESSING (via ``extraction_meta``) 

304# and records the actual chunker params used for that document in the same 

305# format as the ``Chunking <strategy>: ...`` log line (params portion only). 

306# Carrying it forward keeps the value visible after PROCESSING -> FAILED, 

307# whose ``metadata_extra`` only carries timing fields. 

308# ``parse_start_time`` / ``analyzing_start_time`` are Unix epoch seconds 

309# stamped at the entry of ``_parse_worker`` / ``_analyze_worker`` (mirrors 

310# the existing ``process_start_time`` set when entering PROCESSING) so 

311# per-stage durations can be derived from doc_status post-mortem. 

312# ``parse_end_time`` is the paired Unix epoch seconds stamped by 

313# ``_parse_worker`` when the parse stage actually runs (cache-miss branch, 

314# covering ``parse_native`` too which has no cache concept). Absent on 

315# cache-hit attempts (``parse_stage_skipped`` is set instead). 

316# ``analyzing_end_time`` is the paired Unix epoch seconds stamped by 

317# ``_analyze_worker`` only when ``analyze_multimodal`` returns with 

318# ``multimodal_processed=True`` (the explicit "fully completed" sentinel). 

319# It is intentionally NOT stamped on soft-swallowed exception paths or on 

320# malformed/empty sidecar early returns inside ``analyze_multimodal``, so 

321# operators can distinguish "analyze actually completed" from "analyze 

322# attempted but bailed". 

323# ``parse_stage_skipped`` is written by ``parse_mineru`` / ``parse_docling`` 

324# when the raw bundle cache is valid and the parse stage round trip is 

325# skipped; absence == not skipped (e.g. native parser, or cache miss). 

326# ``analyzing_stage_skipped`` is its analyze-stage counterpart, written by 

327# ``analyze_multimodal``'s three user/config early-return branches (no 

328# blocks_path, blocks file missing, or user opted out of every i/t/e 

329# modality). Soft-swallowed exception paths are intentionally NOT considered 

330# "skipped" — they write neither end_time nor skipped (failure is its own 

331# state, captured via the FAILED transition's ``error_msg``). 

332# Within each stage, the ``*_end_time`` and ``*_stage_skipped`` fields are 

333# mutually exclusive (at most one is written per attempt; both may be 

334# absent if analyze soft-failed). 

335# ``source_file`` records the original pending-parse source basename used 

336# by parser workers; it is intentionally separate from canonical ``file_path``. 

337# 

338# The order of this tuple is the rendering order of metadata fields in 

339# the WebUI ``DocumentStatusDetailsDialog`` (carry-over builds the new 

340# metadata dict by iterating this tuple, and dict / JSON / JSX preserve 

341# insertion order all the way to the rendered output). Keep fields 

342# grouped by stage: parse-stage fields together, analyze-stage fields 

343# together, etc., so the dialog reads top-to-bottom along the pipeline.
