1"""Per-write ordering token for the file-backed vector stores. 

2 

3``NanoVectorDBStorage`` and ``FaissVectorDBStorage`` keep a redo log of 

4materialized-but-unsaved upserts. After a reload the flush has to 

5decide, for every logged row, whether the row a *foreign* writer committed 

6under the same (content-hash) id meanwhile is newer than the logged one: a 

7strictly newer row must be left alone (it is a completed reprocess), an older 

8one must be overwritten by the replay. 

9 

10``__created_at__`` alone cannot answer that. ``upsert`` stamps 

11``int(time.time())``, so two writes inside the same second carry the *same* 

12timestamp — a normal, reachable outcome rather than an anomaly — and a tie used 

13to fall through to "replay", which let a stale redo record overwrite a 

14genuinely newer durable row. 

15 

16``__write_seq__`` carries the ordering instead. It is stamped into the record 

17at ``upsert`` time next to ``__created_at__``, persisted with the record, and 

18therefore survives the save/reload round-trip the redo log depends on. Two rows 

19that both carry it are ordered by it alone; ``__created_at__`` decides only 

20when one of them predates the token (see ``row_is_strictly_newer``). Its value 

21is a nanosecond wall-clock reading bumped past the last value this process 

22handed out, so it is: 

23 

24* **strictly increasing per process** — a coarse clock (Windows' ~15ms 

25 granularity) or a backwards NTP step still yields distinct, ordered tokens 

26 for our own successive writes; 

27* **comparable across processes** sharing a store — they share one host clock, 

28 the same assumption ``__created_at__`` already makes for the whole-second 

29 comparison. Comparable, not totally ordered: two processes reading one clock 

30 tick stamp the same token (last limit below). 

31 

32Three limits are deliberately left in place rather than papered over; each 

33resolves to the pre-token behavior (the tie replays), and the comparison 

34helper repeats them where they bite: 

35 

36* it orders *stamp* time, not *commit* time — a writer that stamps late and 

37 commits early is still ordered by when it stamped, which is the intent 

38 order the supersede rule wants; 

39* a row written before this field existed carries none, so a comparison 

40 involving such a row falls back to whole seconds, which a backward clock 

41 step can misorder — the fallback can only be as good as the field it has; 

42* the bump is monotonic **within one process**, which leaves two cross-process 

43 gaps. Two processes reading the same clock tick get the *same* token, so 

44 their tokens tie: that window is one tick wide, not one second — on Linux 

45 ``time.time_ns()`` is ``clock_gettime(CLOCK_REALTIME)`` at 1ns resolution, 

46 so the tie needs the same nanosecond, and where it is genuinely reachable 

47 is Windows before Python 3.13, whose ``time.time()`` reads 

48 ``GetSystemTimeAsFileTime`` (~15.6ms granularity). And because the bump is 

49 a high-water mark, a process that once read a far-future clock keeps 

50 stamping above the corrected clock, so its rows look newer than another 

51 process's until the gap closes. Reaching either also takes two processes 

52 writing the *same id* in that window, which the backends' *Single writer 

53 per workspace* invariant excludes — and the sequential dead-process handoff 

54 the supersede rule exists for puts the two stamps a detection interval 

55 apart, far wider than a tick. Closing them for real would take a totally 

56 ordered generation shared across processes (a counter in 

57 ``shared_storage``, one RPC per upsert batch); folding the pid into the 

58 token would only hide a tie behind an arbitrary winner, so neither is done 

59 here. 

60""" 

61 

62import threading 

63import time 

64 

65# Record key the token is stored under. Dunder-prefixed like ``__id__`` / 

66# ``__created_at__`` so it cannot collide with a ``meta_fields`` name, and 

67# stripped from the public read results (``_format_record`` / ``query``) — 

68# it is storage bookkeeping, not payload. 

69WRITE_SEQ_FIELD = "__write_seq__" 

70 

71_seq_lock = threading.Lock() 

72_last_seq = 0 

73 

74 

75def next_write_seq() -> int: 

76 """Return a strictly increasing per-write ordering token. 

77 

78 Callers stamp one token per ``upsert`` call (every row in that batch 

79 shares it): the token orders *writes*, and the redo-log comparison only 

80 ever puts rows from two different writes side by side. 

81 """ 

82 global _last_seq 

83 with _seq_lock: 

84 seq = max(time.time_ns(), _last_seq + 1) 

85 _last_seq = seq 

86 return seq 

87 

88 

89def row_is_strictly_newer(candidate: dict | None, reference: dict, /) -> bool: 

90 """True when ``candidate`` was written strictly after ``reference``. 

91 

92 Both are stored/logged records. When **both** carry ``__write_seq__`` the 

93 token decides on its own; ``__created_at__`` is consulted only when one of 

94 them predates the token. That precedence is deliberate: the token is the 

95 field built to order writes, and subordinating it to whole seconds would 

96 throw away exactly the guarantee ``next_write_seq`` provides — a clock 

97 stepped backward across a second boundary makes the *later* write carry the 

98 *smaller* ``__created_at__``, and comparing seconds first would declare it 

99 older without ever reading the token that says otherwise. With a sane clock 

100 the two fields agree, so the precedence only shows up under a clock anomaly, 

101 which is the case the token exists for. 

102 

103 A missing token is *not* treated as "older": a legacy row carries none, and 

104 reading its absence as ``0`` would declare it older than any freshly 

105 stamped row and let the replay overwrite it. Such a pair falls back to 

106 whole seconds — so a legacy row from a newer second still wins — and an 

107 equal second is a tie, which resolves to False: the pre-token behavior (the 

108 replay proceeds, the read paths serve the logged record). 

109 

110 Equal tokens resolve to False for the same reason, and are not only a 

111 same-write artifact: the bump that keeps tokens distinct is process-local, 

112 so two processes reading one clock tick stamp the same token (see the 

113 module docstring for how narrow and invariant-violating that is). Ordering 

114 them would take a generation shared across processes. 

115 """ 

116 if candidate is None: 

117 return False 

118 candidate_seq = candidate.get(WRITE_SEQ_FIELD) 

119 reference_seq = reference.get(WRITE_SEQ_FIELD) 

120 if candidate_seq is not None and reference_seq is not None: 

121 return candidate_seq > reference_seq 

122 return candidate.get("__created_at__", 0) > reference.get("__created_at__", 0)
