34class JsonKVStorage(BaseKVStorage): 

35 """JSON-file-backed KV storage with **shared in-memory state across processes**. 

36 

37 A *fundamentally different* cross-process model from 

38 ``NanoVectorDBStorage`` / ``FaissVectorDBStorage`` / ``NetworkXStorage``, 

39 which keep one in-memory copy per process and reconcile via file reloads. 

40 Compare carefully before changing either side. 

41 

42 **Full contract: ``docs/design/FileBackedSnapshotContract.md``** (see its 

43 ``JsonKVStorage`` section) -- the reversed flag semantics, lock scope, 

44 commit granularity and what it means for chunk tracking, and the caveats. 

45 

46 ``self._data`` is NOT a per-process dict: it is a reference into 

47 ``shared_storage._shared_dicts``, a ``Manager().dict()`` proxy every worker 

48 sees the same instance of (a plain dict in single-process mode). A mutation 

49 in any process is immediately visible in every other -- there is no reload, 

50 and adding a ``_get_*`` entry method would be wrong. The on-disk file is 

51 for durability only: read once in ``initialize``, written by 

52 ``index_done_callback``, and not on the steady-state path. 

53 

54 ``storage_updated`` means the OPPOSITE of what it means in the file-backed 

55 classes: ``True`` is "there is dirty data still to flush", never "there is 

56 fresher data on disk to reload". 

57 

58 ``_storage_lock`` is held over EVERY ``self._data`` access, read or write, 

59 because the Manager proxy is not free-threaded across processes. 

60 

61 A commit rewrites the whole namespace, so any writer's flush durably 

62 publishes every other writer's pending mutation here. That matters most for 

63 the chunk-tracking namespaces, whose rows carry purge attribution. 

64 

65 Supported for small-scale testing and validation only. 

66 """

134 async def index_done_callback(self) -> None: 

135 """Flush dirty in-memory state to disk and clear all dirty flags. 

136 

137 Commit point in the shared-memory protocol (see the contract doc, 

138 *Reversed flag semantics*). Steps: 

139 1. Under ``_storage_lock``, check this process's 

140 ``storage_updated.value``. If ``False``, nothing to do — 

141 return. 

142 2. Snapshot ``self._data`` (converting from ``Manager.dict`` 

143 proxy to a plain ``dict`` so the JSON encoder doesn't trip 

144 over the proxy) and write it via ``write_json``, which runs 

145 in the storage-IO pool rather than on the event loop. The 

146 snapshot is taken here, on the loop, so the worker thread 

147 only ever reads a private dict. 

148 3. If ``write_json`` reports sanitization was applied, the 

149 on-disk file no longer matches what was in memory — reload 

150 the cleaned data back into ``self._data`` under the same 

151 lock so the shared view stays consistent. 

152 4. ``clear_all_update_flags`` — wipe every process's 

153 ``storage_updated`` flag back to ``False``, signaling 

154 that the dirty data has been persisted.

156 Note the **semantic difference** from the file-backed classes' 

157 commit: there is no ``set_all_update_flags`` here. The shared 

158 dict is already consistent across processes; the only thing 

159 ``index_done_callback`` does globally is *clear* the dirty

314 async def upsert(self, data: dict[str, dict[str, Any]]) -> None:

316 

317 Two side effects under ``_storage_lock``: 

318 1. Stamp ``create_time`` / ``update_time`` / ``_id`` on each 

319 value, then ``self._data.update(data)``. Timestamping 

320 follows the ``BaseKVStorage.upsert`` contract: a new key 

321 gets both stamps, an existing key keeps its stored 

322 ``create_time`` (``0`` when the row never had one) and only 

323 advances ``update_time``, and a caller-supplied 

324 ``create_time`` is ignored. No I/O is needed for that -- 

325 unlike the remote backends, the previous value is already in 

326 shared memory. Because 

327 ``self._data`` is the shared ``Manager.dict()`` proxy, the 

328 update is visible to all processes immediately — no 

329 reload needed. 

330 2. ``set_all_update_flags`` — flip every process's 

331 ``storage_updated.value`` to ``True``. Here ``True`` 

332 means *"there is dirty data that still needs to be 

333 flushed to disk"*, **not** *"there is fresher data on 

334 disk"* as in the file-backed classes (see the contract doc 

335 for the contrast). 

336 

337 Persistence is deferred to the next ``index_done_callback`` (the 

338 pipeline calls this via ``_insert_done()`` after each batch). 

339 

340 Note: the per-key prep loop calls ``_cooperative_yield`` inside 

341 the lock. That is safe because ``NamespaceLock`` is non- 

342 reentrant — siblings waiting on this lock stay blocked across 

343 the yield; only unrelated coroutines benefit from the yield.
